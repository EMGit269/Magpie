# Magpie Agent 根因检查（2026-10-19）

结论：当前实现把建模规划、端口选择、数据树匹配、错误恢复和结果验收都交给模型的工具调用循环，但宿主接口没有提供完整的观测与修改能力，运行时也没有独立的验收和恢复流程。因此模型的一次小错误会演变成加线、检查、删节点、重建、再检查的长循环。改提示词和增加调用次数不能补齐这些能力。

**检查范围与证据边界**

读取了最新原生 WebView 中保留的完整工具结果、服务日志、历史会话文件、实际发布给模型的工具 schema，以及 Python runtime、Mac Bridge 和聊天界面的代码。未调用模型生成新任务，未修改用户画布或对话。在独立、未显示的 GH_Document 中复现了连线和列表匹配行为。

最新任务是“做一个能修改长度、高度和厚度的墙体，在上面开3层窗洞，每层四个”，session 为 ce6a0f0aece7424287a4f5e3f101f6f4。

- 98 次宿主工具调用：31 次连线、23 次上下文查询、11 次创建图、10 次检查错误、10 次重算、8 次删除组件、5 次组件目录查询。
- 成功创建累计 43 个组件，删除工具执行 8 次；4 次工具执行直接失败，但更多几何错误隐藏在 status=ok 的结果中。
- 页面有 20 段 assistant 文字；工具结果按紧凑 JSON 计算约 169,693 字符。对应请求日志有 74 条 DeepSeek 模型接口 HTTP 200 记录；这不是独立推理轮数或计费 token 的精确统计。
- 最后为未说完的“我先”，随后是 Generation stopped；没有最终完成事件。
- 会话持久化文件只有用户请求，没有工具记录、阶段状态和中间进展。
- 检查时当前画布为空，不能据此判断历史几何由谁、何时清除；历史结论来自当时返回的工具结果，不是当前画布复验。

临时诊断材料保存在 /tmp/magpie-audit-events.json、/tmp/magpie-root-reproduce.json。它们不是产品已有的审计日志。

**1. 工具契约没有成为模型可用的类型约束**

位置：app/tools.py 的 ToolRegistryService._build_host_tools；HostBridge/GrasshopperHostToolExecutor.cs 的 GetFormalHostToolSpec。

宿主 input_schema 是字段列表，Python 将其拼到 description；真正提交给模型的 parameters 只有可选 arguments: object，additionalProperties=true。必填字段、整数端口、GUID、数组元素结构、数量约束都没有成为实际 schema。

实际导出 connect_components 的 OpenAI 工具定义确认了这一点。类型校验还接受了 arguments={from_id:123,to_index:"bad",unexpected:true}，既没有必填目标，也有错误类型。

本次出现两次目录参数错误、一次 Volume 同名歧义、一次虚构/失效实例 ID。原始调用参数没有完整持久化，不能断言两次目录错误的具体参数内容。宽泛 schema 缺陷是独立复现并经代码确认的通用问题。

应改为完整 JSON Schema，包含嵌套组件和连线规格、required、范围与互斥条件；将 schema 转成真正的工具参数模型，而不是描述文字。实例 ID 与组件类型 GUID 分开表示，构建前校验实例存在、端口范围、别名作用域和可用类型转换。

**2. 修改图的能力不完整，纠错会持续增加错误状态**

位置：MacBridge/MacDocumentBackend.cs 的 ExecuteConnectComponents、ExecuteCreateComponentGraph；MacBridge.Tools 清单。

connect_components 只执行 AddSource，接入新来源不会替换旧线。工具中没有断开线、替换输入来源、批量修改已有图、设置端口数据映射的完整能力。创建图虽有本批回滚，但目标限于新组件；不能把“建新节点、替换旧线、删除旧节点”作为一个完整事务提交。

本次模型说“把栅格步长转换为向量”后，新向量加上了，旧 Number 来源仍在，因此同样的 Number→Vector 错误继续存在。它随后只能删掉 Move 再重建。数字端口也可能因旧线与新线同时存在而混入其他值，日志中 Multiplication 最终输出了 Vector。

独立 GH 文档复现：同一输入先 AddSource(a) 再 AddSource(b)，SourceCount=2，明确不是替换。

应提供显式 append/replace、disconnect 和原子的图 patch，执行前检查依赖与变更版本，提交后返回实际来源列表、诊断和变更差异。写操作按依赖顺序执行，只有相互独立的读取并行；网络失败后的重试需要按 request_id 去重。

**3. 对 Grasshopper 核心语义的观测不足**

位置：MacBridge/MacDocumentBackend.cs 的 Describe、DataPreview、SearchComponentCatalog。

当前上下文主要返回输出总数及前 5 条扁平预览。没有分支路径/每分支数量、输入实际数据、完整端口访问与映射状态；一般 Brep 也没有 IsSolid、包围盒、面积、体积等验收字段。目录虽返回输入访问类型，仍不足以观测运行后的匹配关系。

独立 GH 文档复现：4 个点与 3 个位移向量输入 Move，默认输出 4 项；对几何输入 Graft 后输出 12 项、4 个分支。只看总数不能解释数据匹配或布尔分组。

另一个独立复现：矩形曲线沿向量拉伸得到的 Brep，IsValid=true，但 IsSolid=false。本次工具结果确实反复为 Open Brep，模型却称“实心结果”。圆/球的专用预览不能覆盖一般实体建模。

应补充可分页的数据树检查、输入和输出的路径/数量/类型/映射、点和向量坐标，以及通用几何指标。输出截断要显式标注 sampled/truncated 和 total，避免把样本当全集。检查数据时应能直接查询，不必新增 Bounding Box、Volume 等诊断节点污染用户图。

**4. 工具成功、无报错和任务正确没有分开验收**

位置：app/runtime.py 的 ainvoke_stream、invoke；app/workflow.py；AgentRuntime/Web/magpie-shell.html 的 renderEventCard。

当前正常结束就直接产生 completed；没有独立的任务结果验证。提示词要求验证，但程序没有强制执行。MinimalWorkflowService 是另一条简易路径，不是 agent 运行后的自动验收；其中 verifier 也只检查基本摘要/诊断，不能验收几何任务。

check_gh_errors 调用成功时，内部 is_clean=false 仍显示“检查画布错误：已完成”。这表示检查动作完成，不能表示模型正确；界面没有清楚表达区别。

本次有 5 次 is_clean=true，但输出仍是 Open Brep；阵列先为 4，后为 16，又为 4。模型在只有 4 个输出时称“12 个窗户”，诊断中心点还出现 x=10.6，而声称的墙长为 8。模型没有真正建立一致的空间与数量约束。

应先生成可检查的验收项，构建后独立评估。例如此任务要检查单个有效封闭墙体、12 个洞口位置、3 个高度与4列位置、裁剪体穿透厚度、尺寸边界、三根尺寸滑块的真实依赖，并通过临时参数扰动确认参数化行为。未通过时返回部分完成/待修复，不由一段模型文字决定成功。

模型对空间、向量和树匹配的理解也存在实际错误；但目前没有同任务、同工具、同验收条件的模型对比，不能把主要原因归因于 DeepSeek 或声称换模型即可解决。

**5. 执行生命周期与恢复机制不完整**

位置：MacBridge/MacAgentWindow.cs 的 Send；app/runtime.py 的会话写入；app/context_store.py；app/schemas.py。

模型调用轮数和 LangGraph 步数虽然已经解除，但 Mac Send 仍有 CancelAfter(3分钟)。长任务会被客户端取消，取消和手动停止都显示相同的 Generation stopped。没有开始/结束时间及取消原因记录，无法严格判定这一次由计时器还是手动停止触发；固定3分钟截止确实存在。

最近20条会话只包含 user/assistant 字符串。工具轨迹和 ID 映射只存在当轮 agent 内存中；流中断时最终 assistant 也没有写入。下次“继续”必须重新扫描画布，不能可靠恢复阶段或理解已删、已换的节点。

应保存持久化运行记录：run_id、目标、当前阶段、输入输出、别名→实例映射、画布版本、已提交变更和验证结论。中断/断连/关闭/手动停止使用不同结束原因，保留检查点。错误恢复要读取当前状态、解释差异再修复，不靠重放整轮创建。识别重复无进展时应进入诊断和重新规划；不应重新引入固定调用次数预算。

**6. 可观测性和测试使这些问题长期被遗漏**

位置：app/logging_utils.py、app/host_bridge.py；Web UI 的 appendAgentEvent；tests/ 和 MacBridge/tests/。

服务日志没有时间戳和耗时，工具日志只有名称、状态和 ID，缺少持久化参数、结果、状态差异、阶段与取消原因。UI 用工具结果替换工具调用卡，原始参数随之丢失；重新加载历史只恢复文字。

现有测试覆盖基本 CRUD、圆/球、绑定、界面渲染、停止和解除次数限制，但缺少多分支数据树、替换线、封闭实体布尔、参数联动、长时间原生客户端请求及中断续做的完整验收。直接 HTTP 发给服务的测试会绕过原生窗口的3分钟截止，因此证明不了完整产品链路没有时间预算。

应持久化结构化事件（本机保护，不保存 API 密钥），将 UI 作为事件投影；把调用成功和验收成功分开。建立包含跨轮修改、4×3阵列、实体布尔、参数扰动、错误修复、取消续做的场景测试，同时统计成功率、工具次数、修复次数、延迟与上下文大小。

**修复顺序与本次实际变更**

1. 先修执行可靠性：解除 Mac 整轮3分钟截止，保存运行和取消原因。
2. 收紧实际工具 schema，并补齐替换线/断线/原子图修改。
3. 补齐数据树与通用几何观测，提供显式的参数映射配置。
4. 建立“计划→构建→独立验收→定向修复”的流程和可恢复运行状态。
5. 用完整链路场景评估模型和交互表现，再调整提示词、模型和性能。

本次检查已删除 Mac Send 的固定3分钟截止，补充文档并重新构建安装。当前打开的旧程序集不会自动更换 Send 实现，此项需下一次重启 Rhino 才生效；没有为了加载它而关闭现有对话或重启 Rhino。其余项目是经检查确认的待修复项，不表示已经实现。

验证：Mac 正式构建安装成功，0 warnings / 0 errors；现有 Python 单元测试14项通过。独立 GH 语义复现与 schema 导出检查完成。未把这14项已有测试当作长任务、布尔建模或中断续做的验收证明。
